# Synapse Web Client

Веб-клиент мессенджера Synapse на Next.js (App Router) + TypeScript, говорящий с
Go-шлюзом по его собственному бинарному протоколу.

Это **не REST и не GraphQL**. Всё — авторизация, отправка, история, статусы —
идёт одним WebSocket-соединением: кадр `SC`-протокола → varint-конверт →
protobuf-тело. HTTP у сервера есть только для медиа, `/healthz` и `/metrics`.

---

## Быстрый старт

```bash
npm install
```

Запустите сервер (из каталога `server/`):

```bash
go run ./cmd/server
```

> Лежащий в репозитории `server.exe` **устаревший**: он не знает ни `CHAT_CREATE`
> (120), ни появившихся позже `CHAT_LIST`/`CHATS` (123/124) и
> `PROFILE_GET`/`PROFILE_SET`/`PROFILE` (125–127) — и отвечает
> `1000 unsupported message type`. Собирайте из исходников.

Запустите клиент:

```bash
npm run dev
```

Откройте http://localhost:3000. Аккаунта нет — нажмите «Нет аккаунта?
Зарегистрируйтесь»: регистрация идёт тем же кадром `AUTH` с флагом `register`.

## Конфигурация окружений

Адрес сервера нигде не захардкожен. `NEXT_PUBLIC_*` подставляются **на этапе
сборки**, поэтому каждому окружению нужна своя сборка.

| Переменная                   | Назначение                                                             |
| ---------------------------- | ---------------------------------------------------------------------- |
| `NEXT_PUBLIC_SYNCAPP_WS_URL` | Адрес `/ws` шлюза. Пусто → берётся origin страницы (`wss://` на https) |
| `NEXT_PUBLIC_APP_ENV`        | `development` / `stage` / `production`                                 |
| `NEXT_PUBLIC_CLIENT_VERSION` | Уходит в кадре `HELLO`, видно в логах шлюза                            |

Файлы: `.env.development` (авто для `next dev`), `.env.production` (авто для
`next build`), `.env.stage` (подхватывается `npm run build:stage`), `.env.example`
как шаблон.

## Архитектура

### Сетевой слой (`src/shared/api/protocol/`)

Вся протокольная логика собрана здесь и не протекает в компоненты.

| Файл            | Ответственность                                                      |
| --------------- | -------------------------------------------------------------------- |
| `frame.ts`      | Кадр: магия `SC`, версия, флаги, BE-длина, потолок 16 МиБ            |
| `envelope.ts`   | Конверт: LEB128-varint'ы `Type · Seq · Ack · RequestID · len · Body` |
| `codec.ts`      | Тела — protobuf по схеме сервера; `MsgType → protobuf-сообщение`     |
| `msg-type.ts`   | Все типы сообщений (зеркало `pkg/wire/constants.go`)                 |
| `error-code.ts` | Коды ошибок + классы диапазонов (1xxx…5xxx), `ProtocolError`         |
| `caps.ts`       | Битсет возможностей для `HELLO`/`WELCOME`                            |
| `client.ts`     | Машина состояний соединения                                          |
| `generated/`    | Сгенерировано из `body.proto` — **править руками нельзя**            |

**Типы протокола генерируются из схемы сервера**, а не переписываются вручную:
`npm run proto:gen` парсит `server/proto/synapse/v1/body.proto` и кладёт рядом
JSON-дескриптор (для `protobufjs/light` в рантайме) и TS-интерфейсы всех тел.
Схема сервера — единственный источник правды.

Расхождение невозможно только пока команду запускают: генерация ручная, и
`generated/` в репозитории отражает схему на момент последнего запуска. Сервер с
тех пор добавил тела списка чатов и профилей, поэтому перед работой с ними
`npm run proto:gen` нужно прогнать заново — иначе новых типов в клиенте просто
нет.

`SynapseClient` держит весь жизненный цикл:

```
dial → HELLO/WELCOME (согласование возможностей)
     → AUTH или RESUME (личность)
     → рабочий режим: запрос/ответ по RequestID + серверные пуши
     → обрыв → backoff с джиттером → передозвон, по возможности с RESUME
```

Ключевые детали, продиктованные сервером:

- **`RequestID` различает историю и живую доставку.** На `HISTORY` шлюз
  присылает страницу обычными кадрами `NEW` с _нашим_ `RequestID`, а в конце —
  `HISTORY_OK` с курсором. Живой фанаут всегда идёт с `RequestID = 0`. Отсюда
  `requestStream()` рядом с обычным `request()`.
- **`Seq`/`Ack`.** Клиент считает свою исходящую последовательность и
  «подкладывает» максимальный полученный `Seq` в поле `Ack` каждого кадра.
- **Heartbeat.** Сервер пингует каждые 20 с и рвёт связь после 60 с тишины;
  клиент отвечает `PONG` и сам форсирует переподключение после 45 с молчания
  (браузер не всегда замечает мёртвый сокет).
- **Сжатие не запрашивается намеренно.** Шлюз сжимает исходящее, только если
  клиент объявил возможность. У браузера нет zstd-декодера (а серверный zstd
  ещё и со словарём), поэтому мы не объявляем ни `CapZstd`, ни `CapCompression`
  — и гарантированно получаем сырые кадры.

### TanStack Query и Zustand: где что

**TanStack Query** — только там, где у сервера есть настоящий request/response с
кэшируемым результатом:

- `useInfiniteQuery(['history', chatId])` — история с курсором `beforeSeq`
  (`staleTime: Infinity`: история неизменяема, новое приходит пушем);
- `useQuery(['contacts'])` — адресная книга;
- мутации создания чата и работы с контактами.

**Zustand** — клиентское состояние, которого на сервере просто нет:

- `entities/session` — токен и личность;
- `entities/chat` — **реестр чатов** (см. ниже), плюс эфемерные `typing` и чужие
  курсоры прочтения;
- `features/send-message` — исходящая очередь (outbox);
- `entities/settings`, тема, локаль.

Серверные данные в Zustand не дублируются. Живые кадры `NEW` бридж
`features/realtime-sync` пишет **прямо в кэш Query** (`upsertMessage`), а не в
отдельный стор.

**Активный чат намеренно не в Zustand, а в URL** (`/chats/[chatId]`): это даёт
рабочие кнопки «назад», ссылки и перезагрузку без синхронизации двух источников
правды.

`CHAT_LIST`/`CHATS` (123/124) — см. пункт 1 в «Особенностях сервера». Кадр
`DELIVERED` (128) разбирается и доезжает до события `delivered`, но галочки
«доставлено» в интерфейсе пока нет. Транспорты TCP/QUIC браузеру недоступны.

### Секретные чаты (E2E)

> **Аудит 2026-09-18 нашёл два дефекта, унаследованных от серверной реализации,
> из которой сделан этот порт. Оба исправлены:**
>
> - **Проверка подписи предключа стала безусловной** (`shared/lib/e2e/x3dh.ts`).
>   Раньше она выполнялась, только если bundle нёс `signingKey`/`signedPreKeySig`,
>   поэтому каталог ключей, который их не пришлёт, проходил X3DH без
>   аутентификации — защита от MITM снималась удалением двух полей, а не атакой.
> - **Храповик больше не меняет состояние до аутентификации** (`ratchet.ts`):
>   `decrypt` стейджит шаг храповика на копии и принимает её только после
>   успешного `open`, а сообщения по порядку идут отдельной дешёвой веткой.
>   Раньше этот клиент от порчи сохранённого состояния спасало только то, что
>   `decrypt.ts` десериализует копию и пишет её обратно лишь при успехе, —
>   свойство вызывающего кода, а не самого ратчета. Сверх того у карты
>   пропущенных ключей появился суммарный лимит: без него она росла бесконечно,
>   а сохраняется она целиком при каждом сообщении.
>
> **Закрыто с тех пор:** `signedPreKey` ротируется раз в неделю с одним
> поколением grace-копии, пул одноразовых предключей вырос с 8 до 100 и
> автоматически пополняется по нижней границе, появился TOFU-пиннинг ключей
> идентичности с показом safety number (`entities/secret-chat/trust.ts`,
> `features/secret-chats/ui/safety-panel.tsx`), а приватные ключи уехали из
> `localStorage` в IndexedDB под неизвлекаемой обёрткой (`shared/lib/vault`).
> Подробности — в [`server/SECURITY.ru.md`](../server/SECURITY.ru.md) §6.

Полный порт X3DH + Double Ratchet из `server/pkg/e2e` на TypeScript:
X25519 + Ed25519 + HKDF-SHA256 + HMAC-SHA256 + ChaCha20-Poly1305 (библиотеки
`@noble/*`, а не самописная криптография). WebCrypto не подошёл: в нём нет
ChaCha20-Poly1305.

Совместимость задумывалась как проверяемая: `npm run test:secret` и
`npm run test:secret-responder` должны гонять обмен против настоящей серверной
реализации в обе стороны. **Сегодня их нельзя запустить** — оба скрипта требуют
Go-бинарник `e2epeer`, которого в репозитории нет (`server/cmd/` его не
содержит), и CI их не вызывает: web-джоб выполняет только `npm run test`, то
есть vitest. Значит кросс-языковая совместимость сейчас держится на том, что обе
стороны написаны по одним константам, а не на прогоне. Байт-в-байт совпадать
обязаны, в частности:

- порядок DH в X3DH и 32-байтовый префикс `0xFF`;
- info-строки HKDF (`SyncApp-X3DH`, `SyncApp-Ratchet-RK`, `SyncApp-Ratchet-Msg`);
- **JSON заголовка ратчета**: это AD для AEAD, а Go кодирует `[]byte` как
  base64 и пишет поля в порядке объявления (`dh`, `pn`, `n`) без пробелов.

Два места, где протокол вынуждает клиента выкручиваться:

- **Сервер не сообщает, какой одноразовый ключ был выдан.** Директория отдаёт
  запрашивающему один из наших prekey и не говорит публикатору какой. Поэтому
  при первом входящем сообщении перебираются все неизрасходованные кандидаты
  (и вариант «без OPK»), а оракулом служит AEAD — аутентифицируется только
  верный ключ.
- **Истории нет.** Сервер ретранслирует шифртекст и ничего не хранит, поэтому
  переписка живёт только на устройствах-получателях и показана отдельной
  панелью, а не в общей ленте — иначе интерфейс обещал бы синхронизацию,
  которой нет.

**Приватные ключи лежат в IndexedDB под AES-GCM** (`shared/lib/vault`), а
ключ-обёртка сгенерирован браузером как `extractable: false` — его байты не
отдаются скрипту вообще, `exportKey` бросает. Сами ключи ратчета неизвлекаемыми
быть не могут: нужны сырые байты и ChaCha20-Poly1305, которых WebCrypto не
даёт, — обёртка это ближайшее, что предлагает платформа.

Чего это **не** делает: скрипт, уже выполняющийся в этом origin, может позвать
vault ровно так же, как это делаем мы. Разница в том, что однострочный дамп
`localStorage` — самый частый XSS-пейлоад — больше не уносит ключи; атака должна
выполняться в странице и выносить расшифрованное. Поэтому nonce-CSP в
`src/proxy.ts` остаётся более важной защитой, а секретные чаты по-прежнему
привязаны к устройству, а не к аккаунту.

Установки, сделанные до этого изменения, переносятся при первой загрузке: старое
значение читается из `localStorage`, кладётся в vault и **удаляется** оттуда —
оставленный ключ защищён ровно так же, как раньше, то есть никак.

### Push-уведомления

`PUSH_TOKEN` регистрирует Web Push подписку браузера (service worker в
`public/push-sw.js`). Сервер хранит токен как непрозрачную строку и передаёт
`{token, platform}` настроенному HTTP-провайдеру — то есть доставка заработает
только если провайдер умеет Web Push. Нужен `NEXT_PUBLIC_VAPID_PUBLIC_KEY`; без
него кнопка в настройках честно показывает «ключ не задан». Регистрация
намеренно по кнопке, а не автоматически.

### Звонки

Сервер владеет только **сигналингом**: он ведёт список участников и
ретранслирует непрозрачные SDP/ICE между ними, никогда не разбирая payload и не
пропуская через себя медиа. Поэтому клиент строит **mesh** — по одному
`RTCPeerConnection` на каждое чужое устройство в комнате.

Два места, где это легко сделать неправильно:

- **Glare.** Обе стороны могут отправить offer одновременно. Используется
  «perfect negotiation»: роль polite/impolite выводится из сравнения ключей
  `userId:deviceId`, поэтому коллизия разрешается детерминированно, а не как
  повезёт.
- **Изменение состава.** Пиры пересобираются на каждый `CALL_STATE`, а не
  создаются один раз при старте — источник правды по составу всегда сервер.

Разбор ролей: сервер отвечает за комнату (кто приглашён, кто вошёл, когда
завершать), клиент — за медиа.

**NAT.** Шлюз не является STUN/TURN и медиа не видит, так что обход NAT — целиком
задача клиента. По умолчанию используется публичный STUN Google: этого хватает
для большинства сетей, но он раскрывает IP третьей стороне и не проходит
symmetric NAT. Для чего-то серьёзнее демо укажите свой сервер в
`NEXT_PUBLIC_ICE_SERVERS` (JSON-массив `RTCIceServer`); `[]` оставит только
host-кандидаты, чего достаточно в пределах локальной сети.

### Медиа и CORS

Шлюз **не отдаёт CORS-заголовков** ни на одном эндпоинте, поэтому браузер с
другого origin не может сделать `PUT` на `/media/upload/...`: кросс-доменный PUT
не бывает «простым» запросом, preflight `OPTIONS` не обработан, и запрос
блокируется. Клиент решает это без правок сервера — `next.config.ts`
проксирует `/media/*` на шлюз, а выданные им абсолютные URL приводятся к
относительному пути. В продакшене, где приложение и шлюз за одним хостом, это
просто no-op.

## Особенности сервера, под которые пришлось проектировать

Это не догадки — всё вычитано в `server/internal/gateway` и проверено вживую.

1. **Список чатов клиент собирает локально.** Так пришлось спроектировать: у
   `ListUserChats` в сторах не было ни одного типа конверта, который бы до него
   доходил. Поэтому реестр чатов живёт в `entities/chat` (с сохранением в
   localStorage) и наполняется из того, что чат-id всё-таки приносит: `CHAT_INFO`
   при создании, ответ на `JOIN`, входящие `NEW`, черновики, результаты поиска.
   Контакты показаны отдельной секцией как точка входа в новый диалог.

   **С тех пор сервер это закрыл:** `CHAT_LIST` (123) → `CHATS` (124) отдаёт
   страницу чатов с курсором по chat-id, а в строке — тип, название, публичный
   handle, `last_seq`, роль спрашивающего и, для диалога 1:1, id собеседника.
   Клиент их пока не шлёт, так что вкладка в чистом браузере всё ещё стартует
   пустой. Миграция — один запрос после `AUTH_OK` и upsert в тот же реестр;
   локальная сборка остаётся, она держит список свежим между переподключениями.

2. **Личный чат нельзя «создать».** `CHAT_CREATE` принимает только `group` и
   `channel`. Диалог 1:1 возникает сам, когда первое сообщение адресовано
   `@username` — шлюз резолвит хэндл в `resolveChat`. Отсюда экран
   `/chats/new?to=<username>`: он держит `@handle` как цель отправки и подменяет
   URL на настоящий chat-id после первого `SEND_ACK`.
   Побочный эффект: обращение к `@handle` **создаёт** чат, поэтому для такой цели
   мы не запрашиваем историю — иначе открытие экрана набора молча плодило бы
   пустые диалоги.

3. **Имён отправителей в кадрах нет.** `NEW` несёт только `sender_id`, поэтому
   имена собираются из контактов и введённых хэндлов (`entities/user`), а иначе
   показывается сокращённый id. `MsgSearch` — полнотекстовый поиск по
   сообщениям, не по людям.

   **С тех пор появилось чтение профиля:** `PROFILE_GET` (125) принимает id или
   `@username` и отвечает `PROFILE` (127) с именем и аватаром — это и есть
   штатный поиск пользователя (каталога и префиксного поиска по-прежнему нет).
   Клиент его пока не шлёт. Когда пошлёт, `entities/user` станет кэшем ответов
   вместо склада догадок.

4. **Свой курсор прочтения сервер не отдаёт.** `READ` можно отправить, `READ_UPD`
   приходит про _чужие_ курсоры, но спросить свой нельзя. Значит счётчик
   непрочитанного считается на клиенте как `lastSeq - lastReadSeq` (оба —
   серверные последовательности, поэтому счётчик не «уплывает»).

5. **Отправитель получает эхо своего же сообщения** (фанаут шлёт `NEW` всем
   участникам, включая автора). Оптимистичная строка и эхо схлопываются по
   `message_id`/`dedup_key`.

6. **Профиль живёт на сервере** (`features/profile`). `PROFILE_SET` (126) пишет
   имя и `avatar_ref`, `AUTH_OK` возвращает их на каждом подключении, а чужое
   устройство того же аккаунта получает непрошеный `PROFILE` (127) — его ловит
   `realtime-sync` и обновляет сессию, поэтому открытый экран профиля
   переписывается на лету.

   Две детали, которые легко сделать неправильно:

   - **Пустое поле означает «не трогать»,** потому что proto3 не отличает
     отсутствующее значение от пустого. Поэтому снятие аватара — отдельный флаг
     `clear_avatar`, а не пустая строка.
   - **Поле имени следует за сервером, пока в него не начали печатать**
     (`draftName === null`). Иначе начальное значение, взятое до гидратации
     сессии, навсегда осталось бы пустым — и изменение с другого устройства
     затиралось бы тем, что лежало в поле.

   Аватар — обычный `media_ref`: `MEDIA_INIT` → подписанный `PUT` → `PROFILE_SET`
   с полученным ref. Сначала загрузка, только потом запись профиля — ref
   несостоявшейся загрузки не должен попасть в профиль.

7. **Галочка «доставлено» разобрана, но не показана.** `DELIVERED` (128)
   поднимает тот шлюз, который реально записал кадр в сокет получателя, — шаг
   между «сохранено» и «прочитано». Кадр декодируется (тело — `ReadUpdate`, тот
   же курсор, что у прочтения) и доезжает событием `delivered`, но отдельной
   галочки в интерфейсе пока нет.

8. **Токен неизбежно попадает в JS.** Он приходит в теле `AUTH_OK` по сокету;
   HTTP-эндпоинта авторизации у сервера нет, значит httpOnly-cookie серверу
   поставить неоткуда. Токен лежит в localStorage — осознанный компромисс,
   а не недосмотр. Автологин переиспользует токен вместо пароля; при
   auth-ошибке (2xxx) сессия чистится и пользователь уходит на `/login`.

## Надёжность и офлайн

- **Идемпотентность.** У каждого сообщения свой `dedup_key`, стабильный между
  повторами: сервер держит уникальный индекс `(sender_id, dedup_key)` и на
  повтор возвращает уже сохранённое сообщение (`duplicate: true`), не занимая
  новую позицию в чате. Поэтому переслать всю очередь после обрыва безопасно.
- **Outbox** переживает перезагрузку (localStorage): сообщение рисуется сразу,
  ставится в очередь и помечается доставленным только по `SEND_ACK`. Ошибки,
  которые повтор не исправит (`forbidden`, `bad arg`), помечают сообщение
  неудачным с кнопкой «Повторить»; всё остальное остаётся в очереди.
- **Переподключение** — экспоненциальный backoff с полным джиттером, при
  возможности через `RESUME` (сервер переигрывает пропущенные кадры из буфера).
- **Баннер соединения** показывается только при проблемах и отдельно различает
  «браузер офлайн» и «сокет упал, переподключаемся».

## Интернационализация и тема

- Русский и английский, словари в `shared/i18n/dictionaries.ts`. `en` —
  эталонная форма: недостающий ключ в другой локали ловится компилятором.
- Светлая/тёмная/системная тема; выбранная применяется inline-скриптом **до**
  первой отрисовки, поэтому тёмная тема не мигает белым.
- Токены палитры названы по роли (`surface`, `ink`, `accent`, `line`).
  Имена вроде `base`/`sm` не используются намеренно: `--color-base` создал бы
  утилиту `text-base`, перебивающую одноимённый размер шрифта в Tailwind.

## Известные ограничения

- Реализован транспорт `WebSocket`; TCP/QUIC-пути сервера браузеру недоступны.
- Секретные чаты привязаны к устройству: приватные ключи не покидают браузер, а
  значит переписка не появится на другом устройстве и не переживёт очистку
  хранилища. Безопасные номера (`pkg/e2e/safety.go`) не выводятся в UI, так что
  сверить отпечатки вживую пока нельзя.
- Push доставится только если у деплоя есть VAPID-ключ и провайдер, говорящий на
  Web Push; сам сервер токен не интерпретирует.
- Роль пользователя в чате клиент не знает, поэтому админ-панель показывает все
  действия всем, а отказ приходит от сервера (`forbidden`). Роль теперь есть в
  строке `CHATS` (`my_role`) — но только там, и только когда клиент начнёт этот
  запрос слать; отдельного «какая у меня роль в чате X» в протоколе нет.
- Списка участников чата протокол не отдаёт вовсе: `CHAT_EXPORT` доступен лишь
  владельцу/админу, так что показать «кто в группе» рядовому участнику нечем.
- Свой курсор прочтения по-прежнему не запросить (см. пункт 4 выше), поэтому
  счётчик непрочитанного восстанавливается только из того, что клиент видел сам.
