# Synapse: полное руководство «с нуля»

Это подробный разбор проекта **для новичка**, который впервые открыл этот код.
Читается сверху вниз. Никаких предварительных знаний о мессенджерах не нужно —
только базовое понимание, что такое программа и сеть. К концу вы поймёте
**каждую важную часть**: от собственного бинарного протокола до сквозного
шифрования.

> Аналогия на весь документ: представьте **почтовое отделение большого города**.
> Люди (клиенты) шлют письма (сообщения). Почта их принимает, регистрирует,
> раскладывает по ящикам и доставляет. Synapse — это такая «цифровая почта», но
> для мгновенных сообщений.

## 1. Что это вообще и зачем

Это **бэкенд (серверная часть) мессенджера** уровня Telegram, написанный на языке
**Go**. Он умеет: личные чаты 1-на-1, группы, каналы, доставку и подтверждения,
статус «онлайн», «печатает…», галочки прочтения, работу с нескольких устройств,
редактирование/удаление сообщений, поиск, загрузку файлов, push-уведомления и
**сквозное шифрование** для секретных чатов.

Ключевая особенность — **свой бинарный протокол** вместо привычного HTTP/REST.
Почему? Потому что для мгновенных сообщений важны две вещи: **низкая задержка** и
**постоянное соединение**. Об этом подробно в разделе 5.

Проект — это **рабочий каркас (MVP)**: он реально запускается, компилируется и
проходит тесты. Часть «тяжёлой» инфраструктуры (много регионов, отдельная база
под сообщения) описана как дизайн, но ядро работает по-настоящему.

## 2. Запуск за 2 минуты

Нужен только Go 1.26+. Инфраструктура (база, Redis) не обязательна — по умолчанию
всё работает «в памяти».

```bash
# Терминал 1 — сервер
go run ./cmd/server

# Терминал 2 — Алиса (первый вход = регистрация через флаг -register)
go run ./cmd/client -register -user alice -pass secret123

# Терминал 3 — Боб
go run ./cmd/client -register -user bob -pass secret123
```

В окне Алисы наберите:

```
/to @bob
привет, Боб!
```

Боб увидит сообщение мгновенно. Дальше пробуйте `/hist`, `/search привет`,
`/upload путь/к/файлу`, `/typing`. Полный список команд — реакции, треды,
опросы, звонки, пересылка, самоуничтожение, отложенная отправка, закрепления,
черновики, приглашения, роли — печатается при подключении и разобран в разделе 16.

## 3. Словарь терминов

| Термин | Простыми словами |
|--------|------------------|
| **Клиент** | Программа пользователя (наш CLI, а могло бы быть приложение на телефоне). |
| **Gateway (шлюз)** | «Окошко на почте»: принимает все соединения и говорит на нашем протоколе. |
| **Сервис** | Отдельный кусок логики (авторизация, чаты, сообщения…). |
| **Протокол** | Правила, по которым клиент и сервер обмениваются байтами. |
| **Frame (кадр)** | Один «пакет» байтов в нашем протоколе — как конверт. |
| **Envelope (конверт)** | Содержимое кадра: тип сообщения + служебные поля + тело. |
| **Seq** | Порядковый номер — чтобы ничего не потерялось и не перепуталось. |
| **Ack** | Подтверждение «я это получил». |
| **Event bus (шина событий)** | Внутренняя «доска объявлений»: один сервис написал — другие прочитали. |
| **Fanout (веер)** | Разослать одно сообщение всем нужным получателям. |
| **Snowflake** | Способ выдавать уникальные ID, которые ещё и отсортированы по времени. |
| **E2E** | End-to-end, сквозное шифрование: даже сервер не может прочитать. |

## 4. Архитектура на пальцах

Представьте слои сверху вниз. Клиент сверху, база данных снизу.

```
   Клиенты (телефон=TCP/QUIC, браузер=WebSocket, наш CLI)
        │  говорят на бинарном протоколе
        ▼
   ┌─────────────────────────────────────────────┐
   │  GATEWAY (шлюз)  — internal/gateway          │
   │  • принимает соединения                      │
   │  • проверяет, кто ты (авторизация)           │
   │  • следит за порядком и «живостью»           │
   └───────┬──────────────────────────────┬───────┘
           │ вызывает сервисы             │ доставляет ответы
           ▼                              ▲
   Сервисы (бизнес-логика):               │
   auth · chat · message · presence       │
           │ «пишет в доску объявлений»    │
           ▼                              │
   ШИНА СОБЫТИЙ (event bus)  ─────►  fanout (веер) доставляет
           │                              подписчикам-получателям
     ┌─────┼───────┬──────────┐
     ▼     ▼       ▼          ▼
  поиск  push  модерация   БАЗА ДАННЫХ
                          (Postgres/Redis/в памяти)
```

**Главная идея разделения:** «записать сообщение» и «доставить сообщение» — две
разные задачи с разными требованиями. Запись должна быть надёжной (не потерять).
Доставка должна быть быстрой и массовой (в канале — миллионам). Если их смешать,
медленный получатель затормозит запись для всех. Поэтому между ними стоит
**шина событий** — как противопожарная стена.

## 5. Собственный бинарный протокол — байт за байтом

Это сердце проекта. Файлы: `pkg/wire/`.

### 5.1 Почему не HTTP/JSON?

HTTP — это как отправлять **отдельное письмо на каждый чих** и каждый раз заново
здороваться. Для чата, где сообщения летят туда-сюда постоянно, это дорого. Нам
нужно **одно постоянное соединение**, по которому в обе стороны текут компактные
сообщения. Поэтому мы придумали свой формат — маленький и быстрый.

### 5.2 Frame (кадр) — «конверт с маркой»

Каждое сообщение на проводе выглядит так (файл `pkg/wire/frame.go`):

```
+--------+--------+--------+--------+--------------------+==================+
| 'S'    | 'C'    | версия | флаги  | длина (4 байта)    | полезная нагрузка |
| 0x53   | 0x43   | 0x01   | 0x00   | напр. 0,0,0,17     | (envelope, 17 б.) |
+--------+--------+--------+--------+--------------------+==================+
   \_____ 8 байт заголовка ________________________________/
```

Разберём по частям:
- **`S` `C`** (2 байта) — «магическое слово». Если первые два байта не такие —
  это не наш протокол, сразу отбой. Защита от мусора и сканеров портов.
- **версия** (1 байт) — если однажды поменяем формат, увеличим число.
- **флаги** (1 байт) — включатели. Бит 0 «нагрузка сжата», бит 1 «сжато zstd»
  (иначе gzip); остальные зарезервированы.
- **длина** (4 байта) — сколько байт занимает нагрузка. **Максимум 16 МБ** —
  чтобы злоумышленник не написал «длина = 10 гигабайт» и не съел память.
- **полезная нагрузка** — сам конверт (см. ниже).

> Почему длина отдельным числом? Потому что TCP — это «поток байтов без границ»,
> как вода из шланга. Чтобы понять, где кончается одно сообщение и начинается
> следующее, мы сами пишем длину. Это называется «фреймингом».

### 5.3 Envelope (конверт) — что внутри

Внутри нагрузки лежит **конверт** (`pkg/wire/envelope.go`). Его заголовок —
компактные числа переменной длины (varint), а не JSON, чтобы был маленьким:

```
Тип · Seq · Ack · RequestID · длина_тела · тело
```

- **Тип** — что это за сообщение (см. таблицу ниже).
- **Seq** — порядковый номер сообщения в этом соединении. Растёт на 1. Позволяет
  заметить пропажу и восстановиться после обрыва.
- **Ack** — «я обработал всё вплоть до этого номера». Едет «зайцем» на каждом
  сообщении — дёшево подтверждает получение.
- **RequestID** — «номер заявки». Ответ несёт тот же RequestID, что и запрос, —
  так клиент понимает, на что пришёл ответ, даже если запросов много сразу
  (это называется мультиплексирование).
- **тело** — содержимое конкретного типа. Кодируется в **protobuf** (компактный
  бинарный формат) — схемы в `proto/synapse/v1/`, сгенерированный код в
  `internal/wirepb`, а кодек в `pkg/wire/protocodec.go`. Кодек **сменный**
  (`wire.SetBodyCodec`): есть и JSON-кодек для отладки, но по умолчанию — protobuf.
  Кадр и конверт при этом не меняются — protobuf касается только тела.

### 5.4 Типы сообщений

### 5.5 Рукопожатие: HELLO → WELCOME → AUTH → AUTH_OK

Когда клиент подключается, происходит короткий «разговор» (`internal/gateway/conn.go`):

1. Клиент шлёт **HELLO**: «я версия такая-то, устройство такое-то, умею сжатие и
   переподключение».
2. Сервер отвечает **WELCOME**: «ок, договорились о таких-то возможностях, пингуй
   раз в 20 секунд».
3. Клиент шлёт **AUTH**: логин+пароль (или токен). Флаг `register` отличает
   «создать аккаунт» от «войти»; при регистрации можно сразу передать
   `display_name` (потом имя меняется только через `PROFILE_SET`).
4. Сервер проверяет и отвечает **AUTH_OK** с идентификатором, токеном и самим
   профилем (`username`, `display_name`, `avatar_ref`) — клиент, который вошёл по
   сохранённому токену, иначе не знал бы о себе ничего, кроме id.

С этого момента соединение «живое» и можно слать сообщения.

### 5.6 Надёжность: Seq, Ack, переподключение

Сеть ненадёжна: пакеты теряются, соединение рвётся (метро, лифт). Как не потерять
сообщения?

- Каждое сообщение имеет **Seq** (номер). Получатель видит: пришли 5, 6, **8** —
  значит 7 потерялось, можно попросить заново.
- **Ack** едет на каждом ответе: «дошло до N». Отправитель хранит неподтверждённые
  и при обрыве шлёт их снова.
- При обрыве клиент переподключается и шлёт **RESUME** со своим последним Ack.
  Сервер продолжает с этого места — из короткого **replay-буфера в Redis**
  (`internal/replay`); если буфер не поднят, клиент добирает пропущенное через `HISTORY`.

### 5.7 Ещё три важные вещи

- **Heartbeat (пульс):** сервер раз в 20 секунд шлёт `PING`. Если клиент долго
  молчит (60 сек) — соединение закрывают, чтобы не держать «мёртвые» подключения.
- **Backpressure и QoS-полосы:** исходящее делится на приоритеты — служебное >
  сообщения > «печатает…»/presence, у каждого своя очередь ограниченного размера.
  Под нагрузкой первым отбрасывается эфемерное; если переполняется durable-очередь,
  соединение отключают (клиент потом до-синхронизируется), а не тормозят всех.
- **Сжатие:** большие сообщения (>1 КБ) жмутся **zstd с общим словарём** (словарь
  заранее прогрет частыми токенами протокола → лучше жмёт мелкие кадры), либо gzip.
  При распаковке стоит лимит — защита от «архивной бомбы».

## 6. Путь одного сообщения: от Алисы к Бобу

Соберём всё вместе. Алиса пишет «привет» Бобу.

```
1. Алиса → SEND {чат, ключ_идемпотентности, "привет"}
                                   │
2. Gateway: «Алиса вправе писать сюда?» → да
                                   │
3. message.Send:
     • берёт следующий номер seq для чата     ┐ одна транзакция —
     • сохраняет сообщение в базу              ┘ либо всё, либо ничего
     • пишет в шину событий «message.created»
                                   │
4. Gateway → SEND_ACK Алисе {ID сообщения, seq, время}   ← «доставлено на сервер»
                                   │
                       (шина событий)
                                   │
5. fanout читает событие → находит участников чата → Бобу:
     • Боб онлайн  → NEW {…"привет"…}  прямо в его соединение
     • Боб офлайн  → задание на push-уведомление
                                   │
6. Позже Боб читает → READ → Алисе прилетает READ_UPD (галочки прочтения)
```

**Что здесь гарантировано:**
- Сообщение **не потеряется** (сначала запись в базу, потом событие).
- Внутри чата **порядок строгий** (номер seq растёт без дыр).
- Повтор отправки (Алиса нажала «отправить» дважды из-за плохой сети) **не создаст
  дубликат** — спасает «ключ идемпотентности» (см. раздел 7).

## 7. Как хранятся данные

Файлы: `internal/model` (структуры), `internal/store` (интерфейсы),
`internal/store/postgres/migrations/` (версионированные SQL-миграции golang-migrate,
применяются на старте). Основные таблицы: пользователи, устройства, сессии, чаты,
участники, **сообщения**, статус прочтения, **outbox**.

Три идеи, которые стоит понять:

### 7.1 Snowflake ID — умные идентификаторы
Каждому сообщению нужен уникальный номер. Мы используем **Snowflake**
(`pkg/id`): 64-битное число, в которое зашиты **время + номер сервера + счётчик**.
Плюсы: уникальны без согласования между серверами, и их можно **сортировать по
времени** просто как числа.

### 7.2 Порядок внутри чата — `seq`
У каждого чата есть счётчик `last_seq`. Когда приходит новое сообщение, счётчик
увеличивается на 1 и становится номером сообщения в этом чате. Уникальный индекс
`(chat_id, seq)` в базе гарантирует: **никаких дыр и дубликатов номеров**. Клиенты
показывают сообщения в порядке `seq`.

### 7.3 Идемпотентность — защита от дублей
Клиент прикладывает к каждой отправке **ключ идемпотентности** (случайную строку).
В базе стоит уникальный индекс на `(отправитель, ключ)`. Если то же сообщение
придёт второй раз — база вернёт уже сохранённое, а **новый номер seq не потратится**
(выделение номера и вставка — в одной транзакции). Так повторы из-за плохой сети
не плодят копии.

### 7.4 Групповой коммит — быстрая, но надёжная запись
Узкое место записи — «фиксация на диск» (fsync): на каждое сообщение — отдельная
дорогая операция. **Групповой коммит** (`store/postgres/batch.go`) склеивает
сообщения, пришедшие в окне ~2 мс, в **одну транзакцию с одним fsync** (операторы
конвейеризируются через `pgx.Batch`). На замере это подняло один узел с **230 до
3760 сообщ/с** (задержка p50 832 → 45 мс), **не жертвуя надёжностью** — порядок
seq остаётся точным, а упавший батч откатывается на поштучную запись.

> Хранилище **подменяемо**: по умолчанию всё «в памяти» (`store/memory`), но есть
> реальная реализация на **PostgreSQL** (`store/postgres`). Интерфейсы в
> `store/store.go` позволяют потом вынести таблицу сообщений в отдельную «широкую»
> базу (Cassandra/Scylla) без переписывания логики.

## 8. Шина событий и веерная рассылка (fanout)

**Шина событий** (`pkg/eventbus`) — внутренняя «доска объявлений». Сервис
сообщений повесил объявление «создано сообщение X», а другие сервисы (доставка,
поиск, модерация, push) его прочитали и каждый сделал своё дело. Никто никого не
ждёт напрямую.

По умолчанию шина работает «в памяти»; в проме — на **NATS** (`eventbus/nats.go`).
Важные события (`message.*`, `notify.*`) идут через **durable-консьюмеры
JetStream**: если воркер упал, после рестарта он продолжит с того места, где
остановился, и ничего не потеряет. Чтобы событие вообще не потерялось между записью
в базу и публикацией, используется **транзакционный outbox** (`internal/outbox`):
событие пишется в таблицу `outbox` в **той же транзакции**, что и сообщение, а
отдельный relay (`FOR UPDATE SKIP LOCKED` + `LISTEN/NOTIFY`) уже публикует его в шину.

**Fanout** (`internal/fanout`) — тот, кто читает «message.created» и **разносит**
сообщение всем участникам чата, у кого сейчас открыто соединение (на всех их
устройствах — многоустройственность). Кого нет онлайн — тому ставится задание на
push-уведомление. Если получатель подключён к **другому узлу**, fanout находит его
узел в реестре Redis (`internal/router`) и отправляет доставку туда через шину
(`deliver.<узел>`) — так работает горизонтальное масштабирование на много серверов.

## 9. Presence, «печатает…», галочки прочтения

Файлы: `internal/presence`.

- **Онлайн/был(а) в сети** хранится в Redis (или в памяти) с «протуханием»: сервер
  раз в интервал обновляет ключ; если сервер умер и перестал обновлять — ключ сам
  исчезнет, и человек станет офлайн. Не нужен уборщик.
- **«печатает…»** — эфемерное, нигде не сохраняется: просто прокидывается через
  шину событий соседям по чату.
- **Галочки прочтения** — `READ` двигает «курсор прочтения» пользователя в чате
  (только вперёд), и остальным участникам прилетает `READ_UPD`.

## 10. Медиа: как летают файлы

Файлы: `internal/media`. Главное правило: **файлы НЕ ходят через бинарный
протокол**. По протоколу летает только короткая ссылка (`media_ref`).

Как это работает:
1. Клиент шлёт `MEDIA_INIT` (имя, размер).
2. Сервис отдаёт **подписанную ссылку на загрузку** (`MEDIA_TICKET`). Подпись —
   это HMAC со сроком годности: подделать нельзя, через 15 минут протухает.
3. Клиент **грузит байты обычным HTTP PUT** по этой ссылке — прямо в хранилище
   (локально это папка, в проме — S3/облако + CDN).
4. Клиент шлёт обычное сообщение с `media_ref`. Получатель просит `MEDIA_FETCH` →
   получает подписанную ссылку на скачивание.

Это разгружает протокол от тяжёлых байтов и масштабируется отдельно.

## 11. Поиск

Файлы: `internal/search`. Индексатор **подписан на события сообщений** и строит
«инвертированный индекс» — словарь `слово → в каких сообщениях встречается`.
Запрос `SEARCH` находит совпадения и **фильтрует по правам**: вы найдёте только
сообщения в чатах, где вы состоите. Секретные (E2E) чаты не индексируются — сервер
видит только шифртекст. С базой индекс лежит в **общем Postgres tsvector (GIN)**,
чтобы все узлы читали/писали один индекс; для одноузлового dev есть вариант в
памяти, а позже тот же интерфейс подставит OpenSearch для лучшего ранжирования.

## 12. Модерация и защита от спама

Два уровня:

1. **Флуд-контроль на соединении** (`pkg/ratelimit` + gateway): «дырявое ведро»
   (token bucket). Каждое «дорогое» действие (отправка, поиск, загрузка) тратит
   токен; токены пополняются со временем. Превысил — получаешь `ERROR` с кодом
   `FLOOD` и «попробуй через N мс».
2. **Сервис модерации** (`internal/moderation`) — подписан на события сообщений,
   проверяет запрещённые слова и скорость спама, записывает «инциденты». Он
   **наблюдает и фиксирует**, не тормозя доставку.

## 13. Секретные чаты: сквозное шифрование

Самая «крипто-тяжёлая» часть. Файлы: `pkg/e2e`, `internal/keydir`. Цель:
**даже сервер не может прочитать переписку**. Используются только проверенные,
стандартные алгоритмы — **никакой самодельной криптографии**.

### 13.1 Кирпичики (стандартные алгоритмы)
- **X25519** — способ двум людям договориться об общем секрете, даже если за ними
  подсматривают (математика эллиптических кривых). «Диффи-Хеллман».
- **HKDF-SHA256** — «мельница ключей»: из одного секрета делает много ключей.
- **ChaCha20-Poly1305** — шифрование с проверкой целостности (AEAD): если байт
  подменили — расшифровка провалится.

### 13.2 X3DH — первое рукопожатие
Проблема: Боб может быть офлайн, когда Алиса хочет начать секретный чат. Решение:
Боб заранее выкладывает на сервер **публичные «предключи»** (`internal/keydir`).
Алиса берёт их и с помощью нескольких X25519 вычисляет **общий секрет**. Боб
позже вычислит **ровно тот же секрет** из своих приватных ключей. Сервер видит
только публичные ключи — секрет вывести не может.

### 13.3 Double Ratchet — «храповик» на каждое сообщение
Дальше начинается «двойной храповик» (как в Signal). Идея: **на каждое сообщение —
новый ключ**, и старые ключи невозможно восстановить. Даже если у вас украдут
телефон сегодня, прочитать вчерашние сообщения не выйдет (это «прямая секретность»),
а после обмена парой сообщений связь «самозалечивается» от компрометации.

Реализация (`pkg/e2e/ratchet.go`) и **проверена тестами**:
- переписка туда-обратно расшифровывается верно;
- сообщения, пришедшие не по порядку, всё равно читаются (храним «пропущенные»
  ключи, но не больше 1000 — защита от злого заголовка);
- если подменить хоть бит шифртекста — расшифровка отклоняется;
- одинаковый текст даёт **разный** шифртекст (ключи уникальны).

### 13.4 Роль сервера и мультиустройственная синхронизация
Сервер лишь **пересылает запечатанные конверты** (`SECRET_SEND` → `SECRET_RECV`)
между устройствами и хранит **публичные** предключи всех устройств. Он не может
ни вывести ключ, ни прочитать сообщение.

**Секретные чаты синхронизируются между вашими устройствами** — по модели Signal
(«сессия на каждое устройство»). Как это работает: перед отправкой клиент запрашивает
`KEY_FETCH_ALL` — предключи **всех** устройств собеседника **и всех ваших других**
устройств, устанавливает отдельную E2E-сессию с каждым и шлёт по одному шифртексту
на устройство. Сервер маршрутизирует каждый по адресу устройства. Так сообщение
доходит и до второго телефона собеседника, и до вашего планшета — но сервер по-прежнему
видит только шифртекст. Поиск по секретным чатам по-прежнему невозможен на сервере
(у него нет открытого текста) — это неотъемлемое свойство E2E, а не ограничение синхронизации.

## 14. Безопасность: что защищено

Кратко (полный аудит — в [SECURITY.md](SECURITY.md)):
- **Пароли** — argon2id (медленный, стойкий к перебору), сравнение за постоянное
  время; для несуществующих юзеров всё равно «тратим время», чтобы не выдать,
  какие логины заняты.
- **Токены сессий** хранятся в базе **только в виде SHA-256** — утечка базы не даёт
  рабочих токенов.
- **Парсер протокола** защищён: магическое слово, лимит 16 МБ, защита от
  архивных бомб, и он **фаззится** (2+ млн прогонов случайными данными — ни одного
  падения).
- **Против «слоу-лориса»**: у не-авторизованных строгие таймауты на рукопожатие;
  плюс лимит на число одновременных argon2-хешей — чтобы флуд входов не выел память.
- **Флуд-контроль** на соединении; **троттлинг входа** по имени (против перебора);
  **модерация** на контент.
- **Медиа-ссылки** подписаны и протухают; подделка отклоняется; загружаемые файлы
  проходят **антивирус-скан** (хук, дефолт ловит тест-вирус EICAR).
- **E2E** на стандартных алгоритмах, с проверкой подписи предключей (Ed25519).
- **TLS 1.3** на TCP/WS/QUIC (опционально; `SYNAPSE_REQUIRE_TLS=1` заставляет
  сервер вообще не стартовать без TLS); **RBAC**-роли (admin/moderator) и
  **append-only аудит-лог** для чувствительных операций (вход, экспорт чата).
- **Анти-DoS на приёме**: лимит соединений и их скорости с одного IP отсекает флуд
  и «штормы переподключения» ещё до рукопожатия.
- **Safety numbers для E2E**: два пользователя могут сверить 60-значный отпечаток
  «вне канала» и убедиться, что сервер не подменил ключи (защита от MITM).
- **Устойчивость к сбоям**: circuit breaker + локальный резерв, если Redis отвалился.
- **CI со сканами безопасности**: на каждый push прогоняются govulncheck (поиск
  известных уязвимостей-CVE в зависимостях), gosec (статический анализ), детектор
  гонок и фаззинг парсера.

Что осознанно оставлено «на потом» (уровень развёртывания, не кода): менеджер
секретов (Vault/KMS), завести mTLS в реальную сервис-сетку, вышестоящий L4-скраббер
флуда — всё честно перечислено в SECURITY.md.

## 16. Как потрогать руками

- **Посмотреть протокол в бою:** запустите сервер и клиент (раздел 2). Сервер
  логирует каждое соединение и событие.
- **Прогнать все тесты:**
  ```bash
  go test ./...
  ```
  Особенно интересны `internal/gateway/integration_test.go` (два реальных клиента
  через шлюз: доставка, порядок, идемпотентность, поиск, секретная пересылка,
  источник пересылки и срок самоуничтожения), `internal/rpc/message_test.go`
  (тот же путь через настоящий gRPC-хоп — как во флоте сервисов) и
  `pkg/e2e/e2e_test.go` (шифрование).
- **Пощупать продуктовые фичи** прямо из клиента. Полный список команд печатается
  при подключении; интереснее всего те, где видно поведение сервера:
  ```
  /ttl 30                       дальше всё, что вы шлёте, самоуничтожится
  привет                        через 30 секунд придёт «(deleted)» — сработал репер
  /forward <msgID> <chatID>     копия с пометкой «↪ от кого и откуда»
  /schedule +2m позже           отложенная отправка; /scheduled — список, /unschedule — отмена
  /pin <msgID>                  закрепление приходит всем участникам целым набором
  /draft черновик               прилетит на все ВАШИ устройства и никому больше
  /invite 5 +24h                ссылка на 5 входов и сутки; /invites, /revoke <code>
  /join <code>                  вступление по ссылке (или /join @handle по адресу чата)
  ```
- **Пофаззить парсер** (кидать в него случайные байты и убеждаться, что не падает):
  ```bash
  go test ./pkg/wire -fuzz=FuzzParser -fuzztime=30s
  ```
- **Нагрузочный тест** (сколько сообщений в секунду тянет узел):
  ```bash
  SYNAPSE_SEND_RATE=100000 go run ./cmd/server
  go run ./cmd/loadtest -addr localhost:7000 -conns 200 -msgs 50
  ```
  Выдаёт throughput и перцентили задержки send→ack (p50/p95/p99).
- **«Взрослый» режим** с базой: `docker compose up -d`, затем запустить сервер с
  переменными `SYNAPSE_PG_DSN`, `SYNAPSE_REDIS_ADDR`, `SYNAPSE_NATS_URL`
  (см. [README.md](README.md)).
- **Наблюдаемость:** `docker compose -f deploy/observability/docker-compose.yml up -d`
  поднимает Prometheus + Tempo + Grafana; `/metrics` отдаёт гистограммы латентности,
  а `SYNAPSE_PPROF=1` включает профайлер на `/debug/pprof/`.

## 17. Частые вопросы

**Почему Go?** Отличная многозадачность (горутины) для тысяч одновременных
соединений, быстрый, простой в развёртывании (один бинарник).

**В каком формате тела сообщений?** По умолчанию — **protobuf** (компактный
бинарный формат; схемы в `proto/synapse/v1/`). Кодек сменный: есть и JSON-вариант
для отладки. Каркас (кадр+конверт) бинарный независимо от кодека тела.

**Это можно выкатывать в прод?** Ядро — да, оно production-shaped, и уже
нагрузочно проверено (групповой коммит: ~3760 сообщ/с на узел). Перед боем нужно
добавить оставшееся из SECURITY.md (сделать TLS обязательным, менеджер секретов и
т.д.) и догнать масштаб соединений (см. дорожную карту в ARCHITECTURE.md).

**Где «настоящая» база под сообщения?** Сейчас Postgres (и «в памяти» для демо).
Интерфейс `MessageStore` специально сделан так, чтобы потом подставить
Cassandra/Scylla без переписывания логики — это описано в ARCHITECTURE.md, раздел 8.

**Чем отличается облачный чат от секретного?** Облачный сервер читает (чтобы
синхронизировать между устройствами, искать, модерировать) — это как Telegram.
Секретный зашифрован сквозным шифрованием, сервер видит только шифртекст — это как
Signal. По умолчанию — облачные; секретные включаются по желанию.
