# Synapse — Архитектура бэкенда и системный дизайн

Бэкенд мессенджера уровня Telegram на Go. Этот документ — системный дизайн;
репозиторий — работающий MVP его ядра. Там, где раздел реализован лишь частично,
стоит пометка **[реализовано]**, **[заглушка]** или **[спроектировано]**, чтобы
граница между «рабочим кодом» и «планом» всегда была явной.

**Решения заявлены, а не перечислены.** В каждом разделе — один рекомендованный
дефолт и причина. Отклонения отмечены как компромиссы.

---

## Раздел 1 — Объём продукта

| Уровень | Возможности | Статус |
|---------|-------------|--------|
| **MVP** (этот репо) | 1:1-чаты, модель групп/каналов, отправка/доставка/ack, порядок внутри чата, галочки прочтения, «печатает…», presence/был-в-сети, многоустройственная доставка, edit/delete, подгрузка истории, идемпотентная запись, reconnect/resume, бинарный протокол по **TCP + WS + QUIC** | **[реализовано]** |

| **V1** (этот репо) | Медиа-пайплайн (подписанные URL, AV-скан), push (сменный провайдер), полнотекстовый поиск, модерация/антиабьюз, rate/flood-лимиты, **RBAC + аудит-лог**, **observability-стек** (Prometheus/Tempo/Grafana) | **[реализовано]** |

| **V1 остаток** | QR-логин для десктопа, admin API | **[спроектировано]** |

| **Продуктовая поверхность** (этот репо) | Эмодзи-реакции, треды, типизированные вложения (голосовые, кружки, файлы, картинки), опросы с живым подсчётом, **сигналинг звонков и конференций**, контакты и блокировки, пересылка с указанием источника, самоуничтожающиеся сообщения, отложенная отправка, закреплённые сообщения, черновики между устройствами, публичные адреса чатов, пригласительные ссылки, роли администраторов | **[реализовано]** |

| **V2** | Секретные (E2E) чаты — **Double Ratchet [реализовано] + релей + мультиустройственная синхронизация [реализовано]**; **JetStream durable replay [реализовано]**; multi-region active-active, wide-column хранилище сообщений, федеративный антиабьюз-ML | **[смешанное: крипта+durable-шина готовы, multi-region спроект.]** |

**Явно НЕ в первой версии** (опасная сложность к отсрочке): multi-region-репликация,
собственное wide-column хранилище, exactly-once-семантика, **медиа** voice/video.
Каждое раздувает операционную поверхность при малой пользе для MVP. Старт:
Postgres-only, один регион, at-least-once + идемпотентность.

Две отсрочки с тех пор закрыты, и граница здесь важна: E2E-крипта сделана целиком,
а от звонков — только **сигналинг**. Медиа через сервер не идёт: SDP/ICE он
пересылает не разбирая, а медиа-плоскость (SFU, транскодирование, оценка полосы)
по-прежнему вне объёма. Остальная продуктовая поверхность выше — работа на уровне
сообщений: она переиспользует готовый путь записи, веерную рассылку и авторизацию,
а не добавляет новый ярус.

**Must-have vs опционально:** надёжный упорядоченный обмен, авторизация и reconnect —
обязательны. Typing/presence, edit/delete, сжатие — ценны, но не блокирующие.

## Раздел 2 — Высокоуровневая архитектура

Десять слоёв, каждый — шов, где изолируются ответственность и отказ:

```
                              КЛИЕНТЫ
     (мобильный = TCP/QUIC,  веб = WebSocket, десктоп = TCP, CLI)
                                 │
                     [1] Транспортный слой клиента
            raw TCP ───────┼─── WebSocket (/ws) ─── QUIC (UDP)
                                │
                     [2] Слой бинарного протокола (pkg/wire)
                     framing • конверт • seq/ack • сжатие (тело=protobuf)
                                │
       ┌─────────────────────────▼──────────────────────────┐
       │        [4] REALTIME-ШЛЮЗ  (internal/gateway)       │
       │  [3] сессии/авторизация: рукопожатие, токен, resume│
       │  per-conn seq/ack • backpressure • heartbeat • sink│
       └───────┬───────────────┬───────────────────┬────────┘
               │ gRPC (логич.) │                   │ delivery.Hub
               ▼               ▼                   ▼
    [5] ДОМЕННЫЕ СЕРВИСЫ                        живые соединения
    auth · chat · message(write/read) · presence
              │  outbox → события                ▲
              ▼                                   │ push
    [7] ШИНА СОБЫТИЙ (pkg/eventbus: NATS/mem) ─► [5] fanout/доставка
              │                                   │
     ┌────────┼─────────────┐                     │ offline
     ▼        ▼             ▼                      ▼
 [9] notify [11] media  [12] search      [6] СЛОЙ ХРАНЕНИЯ
  worker    pipeline    indexer       Postgres · Redis · NATS · (S3)
 (реал.)    (реал.)     (реал., PG FTS)
                                        [10] модерация/аудит/RBAC (реал.)
```

**Почему это разделение важно.** Путь записи (надёжность, порядок) и путь доставки
(fanout, presence) — противоположны: запись должна быть согласованной и редкой на
чат; доставка — best-effort и с взрывным веером (пост в канал → миллионы отправок).
Связать их — значит либо медленный потребитель тормозит надёжную запись, либо сбой
записи блокирует всю доставку. Шина событий — противопожарная стена: `message.Send`
завершается, как только строка durable и событие застейджено в **транзакционный
outbox**; всё ниже (fanout, push, поиск, модерация) — независимые потребители,
масштабируются, ретраят и падают по отдельности.

## Раздел 3 — Дизайн собственного протокола **[реализовано: `pkg/wire`]**

**Выбор схемы: фиксированный бинарный заголовок кадра + varint-упакованный
заголовок конверта + типизированное тело.** Причина: фиксированный заголовок
тривиально и быстро парсится и фаззится; varint'ы держат заголовок ~6–16 байт;
тело сменное. **Тело кодируется protobuf** (схемы в `proto/synapse/v1/`,
сгенерированный код в `internal/wirepb`, кодек в `pkg/wire/protocodec.go`); кодек
сменный (`SetBodyCodec`, есть и JSON для отладки). Framing/конверт при этом не
меняются. «Protobuf на всё» для кадра отвергнут: самоописывающий framing с явной
длиной проще сделать стойким к враждебному вводу.

### Framing (`frame.go`)

```
+--------+--------+--------+--------+--------------------+==================+
| 0x53   | 0x43   | VER(1) | FLAGS  | LENGTH (4, BE)     | PAYLOAD (LENGTH)  |
| 'S'    | 'C'    | 0x01   | биты   | uint32 ≤ 16 МиБ    | байты конверта    |
+--------+--------+--------+--------+--------------------+==================+
```

- **Magic** `SC` — дешёвый отсев мусора/сканеров.
- **Version** — растёт только при несовместимых изменениях framing.
- **Flags** — bit0 `COMPRESSED`, bit1 `ZSTD` (иначе gzip); биты 2–7 зарезервированы.
- **Length** — лимит 16 МиБ, чтобы ограничить аллокации (анти-DoS). Медиа не ходит
  кадром — только ссылка.
- WebSocket: одно binary-сообщение WS == один кадр (тот же кодек, `wsconn.go`).

### Конверт (`envelope.go`) — все поля LEB128-varint

```
Type · Seq · Ack · RequestID · len(Body) · Body
```

- **Type** (`types.go`): HELLO, WELCOME, AUTH/OK/ERR, PING/PONG, SEND, SEND_ACK,
  NEW, READ, READ_UPD, TYPING, PRESENCE, EDIT, DELETE, HISTORY/OK, SEARCH,
  MEDIA_*, KEY_* (в т.ч. KEY_FETCH_ALL для мультиустройства), SECRET_*,
  CHAT_EXPORT, RESUME/OK, ERROR — и продуктовые блоки: реакции, треды и опросы
  (80-е), сигналинг звонков (90-е), контакты и блокировки (96–100), пересылка и
  отложенная отправка (101–105), закрепления и черновики (106–112), публичные
  адреса, пригласительные ссылки и роли (113–119), создание чатов и регистрация
  push-токена (120–122). **Номера раздаются блоками по
  областям и никогда не переиспользуются**: неизвестный тип клиент молча
  игнорирует, поэтому перенумерация тихо поменяла бы смысл вместо явной ошибки.
- **Seq** — монотонный порядковый номер отправителя на соединение → порядок +
  детект пропусков + resume. **Весь исходящий трафик идёт через один writeLoop**,
  поэтому Seq на проводе всегда монотонный.
- **Ack** — наибольший непрерывный Seq, обработанный отправителем, **пиггибекается**
  на каждом кадре.
- **RequestID** — корреляция запрос/ответ, независимо от порядка → мультиплекс.

### Поведение

- **Версионирование:** `VER` кадра для несовместимостей; битсет возможностей
  (`Cap`) в HELLO/WELCOME. Неизвестные биты игнорируются → старый сервер и новый
  клиент договариваются о пересечении. **Правило расширяемости:** не перенумеровывать
  `MsgType`/`Cap`, только добавлять.
- **Корреляция / ack / ретраи:** RequestID связывает ответ с запросом; SEND_ACK
  подтверждает durability; клиент ретраит неподтверждённые SEND с тем же DedupKey.
- **Секвенирование / dedup:** per-conn `Seq` упорядочивает транспорт; per-chat
  `Seq` (назначает сервер) упорядочивает сообщения; `(sender, DedupKey)` дедупит
  запись.
- **Heartbeat:** сервер PING'ует раз в 20 с; любой входящий кадр обновляет
  «живость»; 60 с простоя → закрытие. Read/Write-дедлайны на сокете.
- **Reconnect / resume:** при обрыве клиент переподключается, шлёт HELLO затем
  RESUME с `resume_token` + `last_ack_seq`. Сервер валидирует и (в проме) отдаёт
  из короткого replay-буфера в Redis; в MVP — клиент добирает через HISTORY.
- **QoS-полосы / backpressure:** исходящее делится на приоритетные полосы
  (control > messages > typing/presence), каждая — ограниченная очередь. Под
  нагрузкой сначала дропаются эфемерные полосы; переполнение durable-полосы =
  клиент слишком медленный → отключение (до-синхронизируется историей).
- **Сжатие:** **zstd + общий словарь** (согласуется через `Cap`; словарь заранее
  прогрет частыми токенами протокола → лучше на мелких кадрах), gzip как fallback;
  порог ≥ 1 КиБ; распаковка ограничена по длине (защита от zip-бомбы).
- **Коды ошибок:** по диапазонам (`1xxx` транспорт, `2xxx` auth, `3xxx` бизнес,
  `4xxx` троттлинг, `5xxx` сервер).

### Жизненный цикл (отправка → получатель)

```
Alice SEND{chat,dedup=k,text} ─▶ Gateway
  authorize(CanPost) ─▶ message.Send
    InsertMessage (tx: bump chat.last_seq → INSERT + outbox-строка)  [durable]
  ◀─ SEND_ACK{msg_id, chat_seq, ts, dup=false}                       Alice
       relay(outbox) ─▶ шина ─▶ fanout ─▶ members(chat) ─▶ Hub.Route(bob)
          Bob онлайн  ─▶ NEW{...}   на устройства Bob
          Bob офлайн  ─▶ publish notify.push
```

### Анти-реплей и идемпотентность

- **Идемпотентность:** уникальный индекс `(sender_id, dedup_key)`. Повторный SEND
  разрешается в сохранённое сообщение (`Duplicate=true`) и **не тратит номер seq** —
  bump и insert в одной транзакции, поэтому проигрыш дедупа откатывает bump (нет дыр).
- **Анти-реплей (транспорт):** монотонный per-conn `Seq` отсекает повторы на живом
  соединении; межсоединительный replay ограничен session/resume-токенами. Под TLS
  replay уровня записей закрыт самим транспортом.

## Раздел 4 — Модель безопасности

### A. Облачный чат (по умолчанию) **[реализовано: транспорт + серверная синхронизация]**

- **Поток авторизации:** логин/пароль → argon2id → непрозрачный 256-битный
  session-токен + resume-токен (`internal/auth`). Токены хранятся как SHA-256.
- **Крипта транспорта:** TLS 1.3 на краю (raw TCP и WSS), опционально включается
  (`SYNAPSE_TLS_*`). Протокол едет *внутри* TLS — свою транспортную крипту не изобретаем.
- **Session-ключи / привязка к устройству:** одна сессия на (user, device); resume
  восстанавливает без повторной авторизации.
- **Ротация:** session-токены — revoke+reissue; TLS-сертификаты — cert-manager.
- **Что сервер может читать:** весь контент облачных чатов. **Не может** восстановить
  пароли (argon2id, односторонний).

### B. Секретный чат (опционально) **[крипта реализована: `pkg/e2e`; релей + мультиустройство реализованы]**

- **E2E:** **X3DH** + **Double Ratchet** (X25519 + HKDF-SHA256 +
  ChaCha20-Poly1305) — только стандартные, проверенные примитивы. Реализовано и
  протестировано (round-trip, двусторонний обмен, не по порядку, отклонение подмены).
  Signed-prekey подписаны **Ed25519** и проверяются в X3DH (защита от MITM через
  каталог ключей).
- **Мультиустройственная синхронизация:** отправитель через `KEY_FETCH_ALL` берёт
  предключи **всех** устройств собеседника и **своих других**, ставит сессию с
  каждым и шлёт по шифртексту на устройство. Сервер маршрутизирует по устройству и
  видит **только шифртекст**.
- **Что сервер может читать:** только шифртекст + метаданные маршрутизации.

**Компромисс ratchet vs облако:** облако даёт серверный поиск и мгновенный
онбординг устройства ценой читаемого сервером контента; ratchet — сильную секретность,
но без серверного поиска. **Рекомендация:** облачные чаты — дефолт; секретные —
включаемый режим на разговор.

## Раздел 5 — Идентичность, авторизация, сессии **[реализовано: `internal/auth`]**

- **Регистрация/вход:** argon2id (memory-hard, 64 МиБ); сравнение за постоянное
  время; dummy-хеш для неизвестного юзера (анти-перечисление). Явные register/login.
- **Мультиустройство:** у каждого устройства своя сессия + курсор доставки; fanout
  бьёт по всем устройствам пользователя.
- **Refresh/revoke:** сессии несут `expires_at`+`revoked_at`; отзыв мгновенный
  (причина выбрать непрозрачные токены вместо JWT).
- **Троттлинг брутфорса:** попытки входа лимитированы по имени на всех соединениях.
- **Токен-модель — рекомендация: непрозрачные session-токены.** O(1)-отзыв, малый
  размер, без распространения ключей. Короткоживущий JWT — только для stateless-проверок
  на краю, если понадобится. JWT-как-сессия отвергнут (realtime нужен мгновенный отзыв).

## Раздел 6 — Микросервисы (каталог)

Построено по этим границам и запускается **двумя способами**: как модульный
монолит (`cmd/server`, один процесс, in-memory без настройки) **или как отдельно
разворачиваемый флот** (`deploy/microservices`) — каждый сервис отдельным
процессом, общается по **gRPC** на sync-пути и **NATS** на async-пути. Шов —
`internal/gateway/services.go`: шлюз зависит только от интерфейсов сервисов,
поэтому локальный `*auth.Service` и gRPC-`rpc.AuthClient` взаимозаменяемы, а код
обработчиков между двумя топологиями байт-в-байт одинаков. Контракты —
`proto/synapse/v1/services.proto` → `internal/rpc`; демоны:
`cmd/authd|chatd|messaged|presenced|keydird` (gRPC) и `cmd/fanoutd|notifyd|
moderationd|searchd` (воркеры шины) за `cmd/gatewayd`. **Impl** = есть в этом репо.
Сплит **проверен end-to-end** (клиент → gatewayd → authd/chatd/messaged по gRPC с
общими Postgres/Redis/NATS); сетевой хоп gRPC меняет throughput на независимое
масштабирование — осознанная цена, поэтому монолит остаётся дефолтом, пока
конкретному сервису не понадобится масштабироваться отдельно.

| **Realtime Gateway** | Соединения, протокол, auth/resume, маршрутизация | бинарный | — | — | нет (stateless) | — | горизонт., graceful drain | шторм соединений | ✅ |
| **Auth/Session** | Регистрация, вход, валидация, отзыв | gRPC | — | audit.* | users, devices, sessions (PG) | strong | горизонт. | store down → нет входов | ✅ |
| **Chat** | Чаты, членство, authz, выдача seq | gRPC | — | — | chats, members, direct_index (PG) | strong | горизонт. | contention seq (горячий чат) | ✅ |
| **Message Write** | Авторизовать+записать+outbox | gRPC | — | message.created/edited/deleted | messages, outbox (PG→wide-col) | strong per chat | шардинг по чату | write amplification | ✅ |
| **Message Read/Sync** | История, курсоры | gRPC | — | — | messages, read_state | read-your-writes | горизонт. | fanout чтения | ✅ |

| **Audit/Compliance** | Append-only аудит-лог | — | audit.*, abuse.* | — | audit_logs | strong-ish | горизонт. | пропуск лога | ✅ (LogSink) |
| **Observability** | Метрики/трейсы/логи | — | — | — | Prom/OTel/Loki | — | — | перегрузка пайплайна | ✅ (/metrics + tracing) |
| **Admin/Config** | Консоль, флаги, экспорт чата | proto/REST | — | audit.* | config (PG) | strong | малый | злоупотребление правами | 🔶 (экспорт+RBAC есть) |

Внутренний транспорт: **gRPC** для запрос/ответ + **шина событий** для асинхронных
фактов. В MVP это внутрипроцессные Go-вызовы за теми же интерфейсами — вынос механический.
**mTLS + RBAC между сервисами:** RBAC (роль admin) реализован; готовый mTLS-примитив
в `pkg/mtls` (взаимная TLS-аутентификация) — для момента, когда сервисы разъедутся.

**Обе топологии должны нести одни и те же данные, а не только одни и те же вызовы.**
Поле, которое есть в доменном типе, но отсутствует в `services.proto`, ничего не
стоит в монолите и пропадает во флоте — тогда решает деплой, а не код, что увидит
пользователь. Поэтому `SubmitRequest` несёт вложение и TTL самоуничтожения, а ответ
`Message` — вложение, корень треда, счётчик ответов, источник пересылки и срок
жизни: всё, что клиент вообще способен показать. `internal/rpc` проверяется через
настоящий gRPC-хоп (`message_test.go`) именно потому, что такая потеря невидима для
юнит-тестов по обе стороны от него.

## Раздел 7 — Модель данных **[реализовано: `internal/model`, `migrations/`]**

Сущности: `users`, `devices`, `sessions`, `chats`, `chat_members`, `messages`,
`read_state`, `direct_index`, `outbox` (+ спроектированы: `message_versions`,
`notification_jobs`, `abuse_events`).

Продуктовые сущности, добавленные миграциями `000003`–`000010`: `reactions`,
`calls` + `call_participants`, `polls` + `poll_votes`, `contacts`,
`scheduled_messages`, `pinned_messages`, `drafts`, `invite_links`, плюс колонки в
существующих таблицах — `messages.attachment` (JSONB), `messages.thread_root` /
`reply_count`, `messages.fwd_*` и `messages.expires_at`, `chats.username`.

- **Вложение — колонка, а не таблица.** У вложения нет отдельной жизни: оно
  создаётся вместе с сообщением, читается с ним и удаляется с ним. JSONB-колонка
  сохраняет это «один к одному» и избавляет каждое чтение истории от join; байты
  всё равно лежат в объектном хранилище.
- **Источник пересылки — обычные колонки, а не внешний ключ.** Пересылка должна
  пережить удаление оригинала, поэтому хранится *снимок* происхождения. Ссылка либо
  сломалась бы, либо воскресила удалённое.
- **Треды через разрешённый корень.** `thread_root` вычисляется на сервере при
  записи из `reply_to`, поэтому вся ветка делит один корень и тред читается одним
  индексным запросом вместо рекурсивного обхода — а клиент не может подделать
  корень, к которому у него нет доступа.
- **Отложенные отправки живут вне журнала сообщений.** Ожидающая отправка не
  занимает `seq` чата (её отмена оставила бы вечную дыру в беспробельной
  последовательности) и невидима для истории, поиска и рассылки, пока не выстрелит.
- **Самоуничтожение — надгробие, а не удаление**, по той же причине: строка
  уходит, позиция в последовательности остаётся. Частичный индекс по
  `expires_at > 0` держит скан репера в пределах маленького «истекающего» множества.
- **Всё, что только растёт, собирается.** Outbox хранит полную копию каждого
  сообщения, поэтому релей, который лишь помечает строки отправленными,
  превращает таблицу-передачу во второй вечный журнал сообщений; опубликованные
  строки собираются после короткого окна хранения, порциями — чтобы DELETE не
  держал блокировки, которые почувствует путь записи. Отработавшие отложенные
  отправки и простаивающие replay-буферы живут по тому же правилу. Медиа
  удаляется вместе с сообщением, если на него больше никто не ссылается
  (пересылка несёт копию ссылки), и подметается в остальных случаях:
  «самоуничтожение», верное только для текста, — не самоуничтожение.

- **ID — Snowflake (`pkg/id`).** 63 бита: 41 мс + 10 узел + 12 счётчик. Выбран
  вместо ULID/UUIDv7 для сообщений: 64-битные int дёшевы для индекса/хранения,
  сортируемы по времени, кодируют узел — без коллизий на шардированной записи без
  координации. Уникальность узла обеспечивается лизом node-id из Redis
  (`internal/nodeid`) или явным `SYNAPSE_NODE_ID`.
- **Порядок — per-chat `seq`.** `chats.last_seq` инкрементируется атомарно в
  транзакции вставки; `UNIQUE(chat_id, seq)` гарантирует порядок без дыр.
- **Ключи/шард-ключи:** `messages` PK `id`, **шард-ключ `chat_id`**. Индексы:
  `messages(chat_id, seq DESC)` для истории; частичный уникальный
  `messages(sender_id, dedup_key)` для идемпотентности.
- **Retention / hot-cold:** свежие сообщения горячие; старые — в дешёвое хранилище/
  архив; tombstone'ы для аудита. **[спроектировано]**

## Раздел 8 — Стратегия хранения (матрица решений)

| Ответственность | Выбор | Почему | Отвергнуто |
|---|---|---|---|
| Метаданные аккаунтов/чатов | **PostgreSQL** | Целостность, транзакции seq+insert, простая эксплуатация | Mongo (слабые tx), Dynamo (ранняя сложность) |
| Лог сообщений | **Postgres сейчас → Scylla/Cassandra позже** | Просто на старте; `(chat_id, seq)` чисто ложится в wide-column | Kafka-как-хранилище (плохие точечные чтения) |
| Presence/typing | **Redis** (TTL-ключи) | Эфемерно, авто-протухание онлайна, без уборщика | Postgres (write amplification) |
| Шина событий | **NATS JetStream** | Sub-ms fanout + **durable-консьюмеры** (упавший воркер продолжает после рестарта) для `message.*`/`notify.*`; core-NATS для эфемерных `deliver.<node>`/typing/presence. **[реализовано]** | Kafka (выше задержка для realtime) |
| Медиа-блобы | **S3-совместимое + CDN** | Дёшево, durable, подписанные URL, разгрузка байтов | Блобы в БД (никогда) |
| Полнотекстовый поиск | **Postgres tsvector сейчас → OpenSearch позже** | Общий GIN-индекс на все узлы; интерфейс подменяется на OpenSearch для ранкинга. **[реализовано]** | in-memory на узел (ломает мультиузел) |

**Партиционирование:** сообщения по `chat_id`; юзеры по `user_id`. **Репликация:**
Postgres primary + sync standby; Redis-реплика; NATS-кластер. **Согласованность:**
метаданные strongly consistent; сообщения strongly *per chat*, eventually глобально;
presence eventual. **Бэкапы:** WAL-архивирование + PITR. **DR:** кросс-региональная
async-реплика, RTO ≤ 15 мин, RPO ≤ 1 мин. **Postgres-only на старте:** ок до низких
миллионов MAU; первым выносится таблица сообщений — интерфейс `MessageStore` делает
подмену локальной.

**Два пути масштабирования записи уже реализованы** за этим интерфейсом:
шардирование по `chat_id` (`internal/store/sharded`, включается
`SYNAPSE_MESSAGE_SHARD_DSNS`) и опциональная реплика чтения
(`SYNAPSE_PG_REPLICA_DSN`) для истории и галочек. Шард — это **полноценное**
хранилище сообщений, а не частичное: он несёт всю схему и стейджит собственный
outbox, который релей дренит по каждому шарду отдельно (релей, смотрящий только в
primary, тихо потерял бы события всех остальных). Корректность даёт co-location:
`chat_seq` (миграция 000002) обновляется той же транзакцией, поэтому шард,
хранящий сообщения+seq+outbox одного чата, выдаёт беспробельный номер локально —
метаданные чатов при этом остаются в primary.

**Throughput записи — групповой коммит.** Потолок записи на узел — fsync коммита
(одна tx/сообщение = один fsync). **Батчер группового коммита**
(`internal/store/postgres/batch.go`) склеивает параллельные вставки в окне ~2 мс в
одну транзакцию + один коммит, пайплайня операторы через `pgx.Batch` (~2 round-trip
на весь батч). Это подняло замеренный прогон на одном узле с **230 → 3760 сообщ/с
(p50 832 мс → 45 мс)**, **сохранив durability** — выигрыш `synchronous_commit=off`
без его отключения. Per-chat seq остаётся точным; упавший батч откатывается на
per-сообщение транзакции. **[реализовано]**

## Раздел 9 — Поток сообщений и согласованность **[реализовано]**

Цикл: SEND → валидация шлюза → auth/session → authz `CanPost` → **tx { bump
chat.last_seq; insert message; insert outbox }** (durable) → relay публикует
`message.created` → fanout по устройствам членов → инбокс получателя (live push или
history-sync) → SEND_ACK отправителю → позже READ. Ретраи несут тот же DedupKey;
дубликаты отсекаются уникальным индексом; офлайн-получателям — push-джоба.

**Гарантии:**
- **Strongly consistent:** durability + порядок внутри чата (одна tx, уникальный
  seq); auth/session; членство.
- **Eventually consistent:** доставка, галочки, presence, индекс поиска, push.
- **Порядок внутри чата:** да — все видят один порядок `seq`.
- **Глобально без порядка:** между разными чатами глобального порядка нет.
- **Семантика доставки:** **at-least-once с идемпотентными эффектами.** Запись
  идемпотентна по DedupKey; доставки могут повторяться, клиент дедупит по
  `message_id`. Exactly-once на проводе не обещаем (дорого); эффект exactly-once —
  через идемпотентность. **Транзакционный outbox** гарантирует, что событие не
  потеряется между коммитом и публикацией.

## Раздел 10 — Realtime-инфраструктура **[реализовано: шлюз + мультиузел; край спроектирован]**

- **Постоянный TCP + WebSocket + QUIC** — один протокол по всем трём (нативные →
  TCP, браузеры → WSS, мобильные → QUIC/UDP с миграцией соединения при смене сети и
  без head-of-line-блокировки). Один stream-обобщённый кодек. **[реализовано]**
- **Балансировка / маршрутизация — stateless-шлюз.** Шлюз не хранит авторитетного
  состояния → **L4-балансировка на любой узел**; sticky не нужен для корректности.
  **Кросс-узловая доставка**: реестр user→node в Redis + node-таргетированные
  сабджекты шины (`deliver.<node>`). **[реализовано, мультиузел]**
- **Масштаб приёма:** несколько accept-горутин (`AcceptLoops`), а для мульти-процесса —
  `SO_REUSEPORT` (отдельная accept-очередь на процесс). **[реализовано]**
- **Горутины на соединение:** две (reader + writer); живость ведёт **один общий
  reaper на узел** (обход map + ping) вместо таймер-горутины на соединение → ~2
  горутины/conn на миллионах соединений. **[реализовано]**
- **Возобновление сессии** — resume-токен + last_ack_seq; короткий **replay-буфер в Redis**. **[реализовано]**
- **Региональные шлюзы / терминация на краю** — TLS на региональном ingress. **[спроект.]**
- **QoS-полосы:** control > messages > typing/presence; эфемерное дропается под
  нагрузкой раньше durable. **[реализовано]**
- **Штормы переподключений** — jitter-backoff клиента + accept-лимит + resume +
  graceful drain. **[resume+drain реализованы]**

## Раздел 16 — Гайд по реализации на Go **[паттерны реализованы]**

- **Репо:** **монорепо** (один модуль, общий `pkg/`), позже разъезд по деплоям.
- **Контракты:** protobuf для тел протокола (`proto/synapse/v1/`, генерация
  `make proto`); gRPC для API сервисов (пока интерфейсы).
- **Границы пакетов:** `pkg/` переиспользуемое; `internal/` домен; сервисы зависят
  от интерфейсов `store`, не от конкретных БД.
- **Конкурентность:** **две горутины на соединение** (reader + writer); живость —
  **один общий reaper на узел** (обход map + ping) вместо таймер-горутины на
  соединение, поэтому счёт горутин остаётся ~2/conn на миллионах соединений.
  Атомики для seq/живости; ограниченные QoS-каналы для backpressure; `sync.Once`.
- **Проброс контекста:** `context.Context` сквозь сервисы и хранилища; **трейсинг
  пробрасывается через шину** (W3C-контекст в заголовках события).
- **Групповой коммит:** параллельные вставки склеиваются в одну пайплайненную
  транзакцию + один fsync (`internal/store/postgres/batch.go`) — 230→3760 сообщ/с
  на узле, durability сохранена. **[реализовано]**
- **Событийность / outbox:** **транзакционный outbox** реализован (`internal/outbox`,
  `FOR UPDATE SKIP LOCKED` + `LISTEN/NOTIFY`) — событие в той же tx, что и сообщение,
  публикуется в **durable-консьюмеры JetStream**; событие не теряется на крахе, а
  упавший воркер продолжает после рестарта. **[реализовано]**
- **Миграции:** **golang-migrate** — версионированный SQL (`…/migrations/`,
  трекинг `schema_migrations`), применяется на старте через встроенный `iofs`;
  отдельная джоба в проме. **[реализовано]**
- **Пирамида тестов:** юнит (`pkg/wire`, `pkg/e2e`), интеграция (`internal/gateway` —

### Реестр рисков

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Contention seq горячего чата/канала | Ср | Выс | Per-chat sequencer; шардинг горячих каналов; **батчинг seq в групповом коммите (реализовано)** |
| Потолок записи Postgres (fsync коммита) | Выс | Выс | **Батчер группового коммита (реализовано): 230→3760 сообщ/с, durability сохранена** |
| Усиление fanout (каналы) | Выс | Выс | Async fanout, queue-группы, воркеры, offload в push |
| Шторм переподключений после рестарта | Ср | Выс | Resume + jitter-backoff + accept-лимит + graceful drain; повторные отправки в нём — дубликаты, поэтому упавший батч записи **делится пополам**, а не разваливается на транзакцию для каждого сообщения (это обрушило бы запись ровно на пике) |
| Медленные потребители тормозят доставку | Ср | Ср | Ограниченные очереди, drop-and-resync (реализовано) |
| Насыщение записи Postgres | Ср | Выс | **Шардирование сообщений по `chat_id` (реализовано, `internal/store/sharded`)** → Scylla; **реплика чтения (реализовано, `SYNAPSE_PG_REPLICA_DSN`)** |
