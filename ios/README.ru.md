# Synapse iOS

Нативный SwiftUI-клиент к gateway Synapse — Go-серверу из [`../server`](../server).

Сервер **не REST**. Он говорит на собственном бинарном протоколе поверх одного
долгоживущего соединения, и этот клиент реализует протокол с нуля: фрейминг,
конверт, protobuf-тела, handshake, возобновление сессии и конвенцию
стриминговых страниц. Ничего не выдумано — под каждым решением ниже указан код
сервера, из которого оно следует.

English version: [README.md](README.md).

## Протокол, как он реализован

### 1. Фрейм — `server/pkg/wire/frame.go`

```
+--------+--------+--------+--------+--------------------+==================+
| 'S'    | 'C'    | VER(1) | FLAGS  | LENGTH (4, BE)     | PAYLOAD (LENGTH) |
+--------+--------+--------+--------+--------------------+==================+
  0x53     0x43     0x01     биты     uint32               байты конверта
```

Магия — дешёвое синхрослово, чтобы отбрасывать сканеры портов; `LENGTH`
ограничен 16 MiB, чтобы враждебный префикс не заставил зарезервировать гигабайты.
Обе проверки продублированы на клиенте: разбор враждебного *сервера* — та же
задача в зеркале. → [`Sources/Network/Wire/Frame.swift`](Sources/Network/Wire/Frame.swift)

Флаги несут gzip (бит 0) и zstd (бит 1). **Мы не заявляем ни того, ни другого** —
и это решение, а не упущение: gateway сжимает только когда согласованный набор
capability говорит, что пир умеет распаковывать. Не заявив capability, мы
гарантируем, что каждый входящий фрейм — открытый текст, и `Frame.decode` вправе
считать сжатый фрейм нарушением протокола. Фреймы чата — сотни байт; тащить
zstd-декодер вместе с общим словарём сервера ради этого пока не окупается.

### 2. Конверт — `server/pkg/wire/envelope.go`

Пять беззнаковых LEB128-varint, затем тело:

```
Type, Seq, Ack, RequestID, len(Body), Body
```

- `Seq` — наш счётчик на соединение, с единицы, сбрасывается на каждом сокете.
- `Ack` — наибольший **серверный** seq, который мы обработали, едет «прицепом» на
  всём, что мы шлём. Именно это позволяет gateway подрезать replay-буфер без
  отдельного ack-фрейма.
- `RequestID` — корреляция, независимая от порядка: в полёте может быть много
  запросов сразу. `0` — «непрошеный push».

### 3. Тела — protobuf, не JSON

`server/pkg/wire/protocodec.go` ставит protobuf-кодек в `init()` пакета,
безусловно. JSON-фолбэка нет и согласовывать нечего: структуры `wire.*Body` с их
JSON-тегами — это *Go-side* API, а на проводе лежит protobuf по
`server/proto/synapse/v1/body.proto`.

Кодек написан руками — reader/writer proto3 плюс по одной конформности на тело —
а не сгенерирован SwiftProtobuf. Тел около сорока, все плоские, из скаляров и
строк: пара reader/writer оказывается меньшим объёмом машинерии, чем генератор,
который она заменяет, а пакет остаётся **без зависимостей** (и без шага protoc,
который никто не запустит на свежем клоне).

Главное правило реализовано в `ProtoReader`: **неизвестные поля пропускаются по
wire type, а не отвергаются**. Сервер, добавивший поле завтра, не должен ломать
клиент, выпущенный сегодня.

### 4. Жизненный цикл соединения — `server/internal/gateway/conn.go`

```
dial → HELLO/WELCOME (согласование capability)
     → AUTH или RESUME (личность)
     → рабочий режим: запрос/ответ по RequestID + непрошеные push
     → обрыв → backoff с джиттером → повторный дозвон, по возможности с resume
```

Gateway первым читает `HELLO` и закрывается на чём угодно другом. Дальше он
принимает ровно одно из `AUTH` или `RESUME` — поэтому выбор делается в
handshake, а не оппортунистически потом.

- **Heartbeat.** Gateway пингует раз в `heartbeat_ms` (20 с) и убивает соединение
  после 60 с тишины. Мы отвечаем `PONG`, и это же — та клиентская активность,
  которая освежает наш presence-TTL: сервер обновляет его только на входящих
  *клиентских* фреймах.
- **Watchdog живости.** 45 с без единого фрейма — принудительный редайл.
  Уснувший телефон или плохая связь дают сокет, о смерти которого ОС не знает.
- **Resume.** `RESUME` проигрывает пропущенные фреймы из replay-буфера вместо
  того, чтобы перезапрашивать историю по всем открытым чатам. Курсор resume
  переживает переподключения и сбрасывается только после *свежего* `AUTH`: новая
  сессия начинает серверную нумерацию заново с 1, и старый курсор запросил бы
  проигрывание, которого не существует.
- **Восстановимое против терминального.** Отказ в resume (буфер истёк) приводит
  к полному `AUTH` по токену, который у нас всё ещё есть. Ошибка 2xxx — нет:
  повтор не поможет, приложение уходит на экран входа.

### 5. Стриминговые страницы

`HISTORY`, `THREAD` и `CHAT_EXPORT` не отвечают списком. Gateway проигрывает
сохранённые сообщения **обычными фреймами `NEW`** с нашим `RequestID`, а затем
закрывает страницу через `HISTORY_OK` с курсором. Общий `RequestID` — *едиственное*,
что отличает подгруженное сообщение от живого fanout (у которого `RequestID`
всегда 0). Ошибиться здесь — значит вносить каждую страницу истории дважды. На
это есть отдельный тест.

### 6. Ошибки — `server/pkg/wire/constants.go`

Коды сгруппированы по классам в десятичных диапазонах, чтобы клиент мог
реагировать на код, которого никогда не видел:

| Диапазон | Смысл | Поведение клиента |
|---|---|---|
| 1xxx | транспорт/протокол | починить фрейминг, повторить |
| 2xxx | авторизация/сессия | **переаутентификация** — переподключение не поможет |
| 3xxx | права/бизнес-логика | не повторять как есть |
| 4xxx | троттлинг | backoff, уважать `retry_after_ms` |
| 5xxx | сервер | повтор с backoff (запись идемпотентна) |

`ErrResumeExpired` (1004) намеренно **не** в диапазоне авторизации: он
восстановим, и трактовка его как мёртвой сессии выкидывала бы пользователя из
аккаунта на рутинном переподключении.

### 7. Транспорт

Реализованы оба; выбор — значение конфигурации, а не правка кода.

| | Когда |
|---|---|
| **WebSocket** (`URLSession`, `/ws`) — по умолчанию | Проходит прокси и captive-порталы, которые режут незнакомые TCP-порты; системный TLS, переключение на сотовую сеть |
| **TCP** (`Network.framework`, `:7000`) | Без HTTP-апгрейда и WS-маскирования; `NWConnection` сам сообщает о смене Wi-Fi↔LTE |

QUIC (ALPN `synapse-quic`) не реализован: `Network.framework` даёт QUIC-стримы
с iOS 15, но gateway требует под него TLS, а миграция соединения важнее всего на
сети, которой мы пока не управляем. Место для него — протокол `Transport`: один
файл, остальное не меняется.

## Два ограничения протокола

Названы прямо, потому что приложение построено *вокруг* них, а не делает вид, что
их нет.

### Нет сообщения «дай список моих чатов»

`store.ListUserChats` на сервере есть (`internal/store/store.go:71`), но wire-типа
ему не завели. Поэтому список чатов **собирается локально** из всего, что
упоминает чат — входящие `NEW`, `SEND_ACK`, `CHAT_INFO` при создании,
`INVITES.joined_chat` при входе по ссылке, разрешённые `@handle` — и хранится в
SQLite.

Следствие: **свежая установка на новом устройстве стартует с пустым списком** и
наполняется по мере трафика. Два честных способа закрыть дыру, по приоритету:

1. Добавить `MsgChatList`/`MsgChats` в gateway (~40 строк: `ListUserChats` плюс
   `Chat.Get` по id). На клиенте — один метод.
2. Пушить `CHAT_INFO` по каждому чату сразу после `AUTH_OK`.

### Нет API профиля

`display_name` можно передать только при регистрации — и `handlers.go:43`
передаёт пустую строку — обновить его нечем, аватарок в протоколе нет вовсе.
Поэтому имя и символ в настройках **локальны для устройства**, и экран так и
написано говорит, а не намекает, что их кто-то видит. Аватары — цветные
монограммы, выведенные из id пользователя.

Смежное: `AUTH_OK` возвращает id и токены, но не username, и спросить его потом
нечем — приложение запоминает то имя, которое человек ввёл при входе.

### Ещё стоит знать

**Поиск пользователя — только точный handle.** Каталога нет, префиксного запроса
нет. Резолв едет на `PIN_LIST`: он read-only, не тратит flood-бюджет, и его ответ
несёт *разрешённый* снежинка-id — тогда как `HISTORY_OK` возвращает эхом ровно ту
строку, что мы послали. `NOT_FOUND` — нет такого пользователя, `FORBIDDEN` —
блокировка в одну из сторон.

## Архитектура

```
ios/
├── SynapseKit/            SPM-пакет — весь код здесь
│   ├── Package.swift
│   ├── Sources/
│   │   ├── Network/       фреймы, конверт, кодек proto3, транспорты, клиент
│   │   ├── Domain/        сущности, протоколы репозиториев, use cases  (без зависимостей)
│   │   ├── Persistence/   SQLite-кэш, sync engine, реализации репозиториев
│   │   ├── Presentation/  ViewModel + SwiftUI-экраны                  (только Domain)
│   │   └── DI/            композиция зависимостей
│   └── Tests/             NetworkTests, DomainTests, PersistenceTests
├── App/                   оболочка приложения (@main, AppDelegate, Info.plist)
├── Config/                Dev / Stage / Prod .xcconfig
├── Resources/             Strings (en/ru), Assets
└── project.yml            спека XcodeGen
```

Пакет лежит в подпапке, а не в `ios/`, — намеренно. Локальный пакет, чей корень
совпадает с директорией сгенерированного `.xcodeproj`, не резолвится: пакет
содержал бы сам проект, который его подключает. Xcode сообщает об этом как
`no such module` на первом `import` приложения — то есть в месте, не имеющем
отношения к настоящей причине.

Каждый слой — отдельный SPM-таргет, поэтому направление зависимостей проверяет
**компилятор**, а не соглашение: `Presentation` физически не дотянется до
протокола, `Domain` не зависит ни от чего. `ErrorMapping` — единственный файл,
знающий оба словаря: он превращает `ProtocolError` в `AppError` на границе
репозитория, и поэтому ни одной ViewModel не нужен `import SynapseNetwork` ради
кода статуса.

### Offline-first

Одно правило: **всё, что присылает gateway, пишется в SQLite; UI читает только из
SQLite.** Нет пути, на котором экран показал бы то, чего нет в кэше — потеря
связи меняет только *свежесть* данных.

Путь отправки — вся история в одном методе:

1. Оптимистичная строка **с ключом по dedup key** и запись в outbox — одним
   движением. Писать можно с выключенным радио.
2. По `SEND_ACK` строка **повышается на месте**: первичный ключ меняется с dedup
   key на серверный снежинка-id. Список сохраняет identity и не анимирует
   сообщение «наружу и обратно».
3. При переподключении outbox выгружается **от старых к новым и последовательно**:
   gateway выдаёт беспробельный `chat_seq` в порядке прихода, а соединение
   ограничено 20 отправками в секунду — параллельная выгрузка бэклога и
   переставила бы собственные сообщения пользователя, и упёрлась бы в лимитер.
4. Повтор, чья первая попытка на самом деле дошла, возвращается с
   `duplicate = true` и исходным id сообщения. Это успех — ровно для этого dedup
   key и нужен.

Счётчик непрочитанного **вычисляется** (`seq > last_read_seq`), а не хранится:
прочтение с другого устройства чинит бейдж, и рассинхронизироваться нечему.

### Почему SQLite напрямую, а не Core Data / GRDB / Realm

Паттерн доступа не графовый, а запросный: «50 сообщений чата X ниже курсора,
сначала новые» и «чаты по последней активности с вычисляемым непрочитанным» —
это два индексированных SQL-запроса.

- **Core Data** заставил бы выражать их fetch-запросами поверх модели, которой не
  видно в диффе, а её модель конкурентности (контексты, merge policy) — вторая
  система конкурентности под свифтовой.
- **GRDB** — правильная библиотека для этой формы и та, к которой я обычно и
  тянусь. Но она даёт типобезопасный маппинг строк вместо ~250 строк кода в обмен
  на зависимость, которую надо тянуть, пинить и держать в согласии с
  самописным wire-кодеком, у которого зависимостей нет.
- **Realm** приносит свою объектную модель и правила потоков — обязательство
  больше задачи.

Итого: системный SQLite, один `actor` для сериализованного доступа (собственные
режимы многопоточности SQLite — способ бесплатно получить тонкую порчу данных),
WAL и forward-only миграции по `PRAGMA user_version` — версия схемы едет внутри
файла, который описывает.

### Конкурентность

`async`/`await` везде; `actor` — на трёх местах с разделяемым изменяемым
состоянием (`SynapseClient`, `Database`, `SyncEngine`); `AsyncStream` — на всех
наблюдениях. ViewModel — `@MainActor ObservableObject`: `@Observable` требует
iOS 17, а таргет 16.

Чтения — потоки **целых снимков**, не дельт. Для списка чатов и страницы
сообщений это верный размен: кэш — единственный источник правды, снимок не может
разъехаться с ним так, как это делает журнал событий, а SwiftUI всё равно
диффит снимок.

### Где что хранится

| Что | Где | Почему |
|---|---|---|
| Bearer-токен, resume-токен, device id | **Keychain** (`afterFirstUnlockThisDeviceOnly`) | Это учётные данные. *afterFirstUnlock* — чтобы фоновый запуск по пушу мог переподключиться на заблокированном телефоне; *thisDeviceOnly* — чтобы они не уехали в бэкапе на чужое устройство |
| Тема, язык, настройки уведомлений | `UserDefaults` | Не секреты, и нужны синхронно на старте, чтобы первый кадр не мигнул чужой темой |
| Чаты, сообщения, outbox, контакты | SQLite | Запрашиваются, пагинируются и стираются при выходе |

Выход из аккаунта стирает кэш. Мессенджер, показывающий чаты прошлого
пользователя после logout, их уже утёк — что бы ни было написано на экране входа.

## Запуск

### Требования

- macOS с **Xcode 15+** (Swift 5.9), симулятор или устройство на iOS 16+
- [XcodeGen](https://github.com/yonaskolb/XcodeGen) — `brew install xcodegen`
- Go-сервер из [`../server`](../server)

Swift-зависимостей **нет**, проект резолвится офлайн.

### 1. Поднять сервер

```bash
cd ../server && go run ./cmd/server
```

Это даёт WebSocket на `:8080/ws`, сырой TCP на `:7000` и in-memory хранилище —
Docker не нужен. Конфигурация Dev смотрит ровно сюда.

### 2. Сгенерировать проект Xcode

```bash
cd ios && xcodegen generate
```

```bash
open Synapse.xcodeproj
```

Выбрать схему **Synapse Dev** и запустить. Если XcodeGen ставить не хочется:
создать iOS App target в новом проекте, перетащить `ios/` как локальный пакет,
добавить в таргет `SynapseDI` и `SynapsePresentation` и назначить трём
конфигурациям соответствующие `.xcconfig`.

### 3. Проверить

Зарегистрировать `alice` в симуляторе, затем написать ей из CLI-клиента:

```bash
cd ../server && go run ./cmd/client -register -user bob -pass secret123
```

В терминале Боба — `/to @alice` и текст. Сообщение приходит в приложение в
реальном времени; ответ из приложения приходит Бобу в терминал.

### Окружения

| Схема | Конфиг | Gateway |
|---|---|---|
| Synapse Dev | `Config/Dev.xcconfig` | `ws://localhost:8080/ws` |
| Synapse Stage | `Config/Stage.xcconfig` | `wss://stage.synapse.example/ws` |
| Synapse Prod | `Config/Prod.xcconfig` | `wss://synapse.example/ws` |

Значения попадают в приложение через подстановку в `Info.plist` и читаются один
раз в `ServerEnvironment.current` — ни один URL не зашит в место вызова. Переход
на сырой TCP — это `SYNAPSE_TRANSPORT = tcp` в `.xcconfig`.

Дополнительно `ServerEnvironment.current` отказывается уважать
`SYNAPSE_ALLOWS_INSECURE_TLS`, когда окружение `prod`, — ошибка в конфиге не
сможет тихо отключить проверку сертификата в релизной сборке.

### Тесты

⌘U в Xcode или из терминала — обратите внимание на директорию: тесты
принадлежат пакету, а не проекту приложения:

```bash
cd ios/SynapseKit && xcodebuild test -scheme Synapse-Package -destination 'platform=iOS Simulator,name=iPhone 15'
```

Не `swift test`: пакет объявляет единственной платформой iOS, поэтому тесты
гоняются через Simulator, а не на macOS-хосте. `Synapse-Package` — схема, которую
Xcode генерирует для `Package.swift`.

**Нет Mac?** `.github/workflows/ios.yml` прогоняет всё на бесплатном macOS-раннере
GitHub: тесты, сборку приложения и скриншот запуска в симуляторе. Сделайте из
`ios/` отдельный репозиторий (как `server/` и `client/`) и запушьте. Четыре
набора:

- **NetworkTests** — побайтовый фрейминг (магия, big-endian длина, гигантский
  префикс, обрезка), границы varint, порядок полей конверта, эталонные байты
  proto3 и пропуск неизвестных полей, плюс клиент целиком против `FakeGateway`,
  который говорит на настоящем протоколе: порядок handshake, заявленные
  capability, корреляция при двух отправках в полёте, история, не протекающая в
  поток push-ов, `PING`→`PONG` и резолв `@handle`.
- **DomainTests** — правила валидации, существующие из-за поведения сервера, в
  том числе то, где легко ошибиться: `MaxTextLen` — лимит в **байтах**, поэтому
  4200 кириллических символов должны отвергаться, хотя это заметно меньше 8192
  *символов*.
- **PersistenceTests** — идемпотентность по dedup key, повышение оптимистичной
  строки, порядок outbox и сохранность вложения в нём, вычисляемое
  непрочитанное, маркер прочтения, который не едет назад, курсор пагинации,
  игнорирующий неотправленные строки, локальное истечение самоуничтожающихся
  сообщений, last-writer-wins для черновиков и миграции: база v1 обязана дойти
  до v2 *вместе с очередью сообщений*, а не быть пересозданной.
- **PresentationTests** — маппинг темы, фолбэк отсутствующего ключа, штампы
  времени в списке чатов, отмена задач в `TaskBag` при освобождении. Половина
  ценности — в ребре зависимости: набор тянет `SynapseDI`, а с ним и все
  остальные таргеты, поэтому CI компилирует SwiftUI-слой. До него этого не делал
  никто, кроме сборки приложения, где падение выглядит как `no such module` на
  первом импорте и не называет ничего из того, что реально сломано.

## Push-уведомления

Клиентская часть готова: регистрация в APNs, `PUSH_TOKEN` при подключении и
deep link из тапа по уведомлению в нужный чат (в payload сервера есть `chat_id` —
`internal/notify/notify.types.go`). Выключение уведомлений отправляет **пустой**
токен: он стирается на сервере, и пуш останавливается в источнике, а не на
устройстве.

Серверная часть требует одного вашего действия: `notify.ProviderFor` шлёт на
обобщённый HTTP-эндпоинт (`SYNAPSE_PUSH_ENDPOINT`), а не в APNs напрямую, и без
настройки подставляет логгер. То есть пуши дойдут, когда эндпоинт будет смотреть
на APNs-мост:

```bash
SYNAPSE_PUSH_ENDPOINT=https://your-apns-bridge/notify \
SYNAPSE_PUSH_KEY=... \
go run ./cmd/server
```

До этого работает всё, кроме самой доставки — и она видна в логе сервера, а не
пропадает молча.

## Медиа

Байты никогда не едут протокольными фреймами. По два круга в каждую сторону:

- **Загрузка** — `MEDIA_INIT` выдаёт тикет (подписанный URL плюс `media_ref` для
  сообщения), затем HTTP `PUT`. Заявленный размер входит в подпись тикета, и
  сервер держит тело ровно под него, так что размер при init обязан совпасть с
  размером загрузки. Предел — 100 MiB (`maxSize` в `media.New`).
- **Скачивание** — `MEDIA_FETCH` выдаёт подписанный URL с истечением; качаем один
  раз и кладём в `Caches/media/<ref>`: URL протухает, байты — нет.

Автоматически при скролле ничего не качается: каждый забор стоит отдельного
круга за подписанным URL, поэтому вложение — нажимаемая карточка, пока его не
попросят. Метаданные (вид, размер, имя, размеры кадра) едут с сообщением как раз
чтобы карточку можно было нарисовать без блоба. Свои загрузки кэшируются под тем
ref, который вернул сервер, — только что отправленное фото рисуется с диска, а не
скачивается обратно с сервера, куда мы его и отправили.

Загрузка требует связи (тикет выдаётся по протоколу), поэтому, в отличие от
текста, offline не работает — и об этом говорится пользователю, а не молча
ставится в очередь. В очередь встаёт само *сообщение* с готовым ref, для чего у
outbox и появилась колонка вложения (схема v2).

## Черновики

`DRAFT_SET` gateway зеркалит на **другие** устройства пользователя — маршрутизация
по юзеру, не в чат — то есть черновик это продолжение набора на другом
устройстве, а не общий блокнот. Сохранение с дебаунсом 800 мс (зеркало едет по
тому же flood-ограниченному соединению, что и сообщения), а входящий черновик
принимается только когда локальный composer пуст: затирать то, что человек
печатает, потому что другое устройство напечатало своё, — хуже, чем дать им
разойтись. Отправка очищает черновик везде.

## Что подключено, но пока без экрана

Клиент протокола это умеет; экрана нет — по объёму работ, а не по сложности:
треды, закрепления, пересылка, invite-ссылки и роли, отложенная отправка,
опросы, звонки и E2E-секретные чаты. Добавить экран для любого — это ViewModel
поверх уже существующего метода.
